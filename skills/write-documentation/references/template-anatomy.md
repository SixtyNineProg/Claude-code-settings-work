# Template Anatomy

Точная структура каждого DemoBP-шаблона. Открывай этот файл при заполнении соответствующего выходного файла, чтобы соблюсти структуру. Все шаблоны — HTML-фрагменты **без обёртки** (нет `<!DOCTYPE>`, `<html>`, `<head>`, `<body>`, `<style>`).

## Обзорная страница

Шаблон: `DemoBP - Демонстрационный бизнес-процесс.html` → `{bpName}.html`

Структура:
- `<h2>Общее описание</h2>`
- 3 `<p>` абзаца: назначение процесса, индекс трассировки (`DemoBP`), состав документации.
- `<ul>` из 5 `<li><a href="">…</a></li>` — ссылки на разделы: История изменений, Инструкция по развёртыванию, PDD, TD, UG (все с `href=""`).

Замены: `DemoBP` → `{bpName}`, описание назначения — из README.md.

## История изменений

Шаблон: `DemoBP - История изменений.html` → `{bpName} - История изменений.html`

Структура — одна `<table>` с `<thead>` (2 колонки: `Тикет`, `Краткое описание изменений`) и `<tbody>` с одной seed-строкой:
- `RPA-xxxxx` / `Изначальная разработка`

Действие: клонируй seed-строку для каждого тикета. Для нового процесса оставь одну строку с тикетом из названия ветки/задачи (или `RPA-xxxxx` как placeholder, если тикет неизвестен).

## Инструкция по развёртыванию

Шаблон: `DemoBP - Инструкция по развертыванию.html` → `{bpName} - Инструкция по развертывание.html`

Структура — нумерованная `<table>` (без thead, `<tbody>` с 7 строками `<td>номер</td><td>…</td>`):
1. Проверка соответствия [стилю](https://wiki.a1.by/pages/viewpage.action?pageId=453837503) (ссылка постоянная).
2. Подготовка файлов и перенос на прод по [общей инструкции](https://wiki.a1.by/pages/viewpage.action?pageId=474056373) (ссылка постоянная).
3. Создать Ресурсы типа Credential — `<ul>` с `имя_ресурса_1`, `имя_ресурса_2` (placeholder).
4. Создать Ресурсы типа Text — `<ul>` с `имя_ресурса_3`, `имя_ресурса_4` (placeholder).
5. **Опционально** — папка в Хранилище.
6. **Опционально** — Очередь задач.
7. **Опционально** — Триггеры.

После таблицы: `<p>Дополнительные действия…</p>` + `<ol>` с `Действие 1;`, `Действие 2.` (placeholder).

Замены:
- Строки 3–4: подставь реальные имена credential и text-ресурсов из Java (`getCredentials(...)` и `assets().get(...)` вызовы). Имена констант-asset берутся из Java-кода (например `SAP_CREDENTIALS_ASSET`, `SharePointModule.CREDENTIALS_ASSET`).
- Дополнительные действия — из README.md (если есть специфичные шаги развёртывания).

## PDD — Process Design Document

Шаблон: `DemoBP-PDD - Process Design Document - Документ проектирования процесса.html` → `{bpName}-PDD - Process Design Document.html`

Самый большой файл (371 строка). Состоит из 10 якорных секций `<h2 id="…">`, каждая со своей таблицей. Заголовки секций и их ID **нельзя переименовывать** (на них ссылаются кросс-ссылки).

### `id="Общая информация"` — Общая информация
Одна `<table><tbody>` с 9 строками вида `<td><strong>Лейбл</strong></td><td>значение</td>`:
1. **Процесс** — `{bpName} / {bpDescription}`
2. **Название бизнес-процесса** — `{bpName} / {bpDescription}`
3. **Управление** — `Группа разработки и поддержки роботизированных решений`
4. **Версия и место хранения бизнес-процесса** — `<a href="">` ссылка на GitLab (placeholder `href=""`; подставь реальный URL репозитория процесса, если известен, иначе оставь `href=""`).
5. **Владелец бизнес-процесса** — `—` (или из README).
6. **Пользователи бизнес-процесса** — `—`.
7. **Связанные документы** — `<ul>` со ссылками на `{bpName}-TD` и `{bpName}-UG`.
8. **Верифицировано** — `—`.
9. `Статус документа` (без strong) — `DRAFT {дата}`.

### `id="Используемые системы"` — Используемые системы
`<table>` с `<thead>` из 3 колонок: `Наименование (полное)`, `Наименование (сокращение)`, `Примечания`. `<tbody>` — по одной строке на каждую систему из анализа импортов (шаг 4). Минимум: Sherpa Orchestrator + Почтовый сервер.

### `id="Описание процесса"` — Описание процесса
- `<table><tbody>` 1-колоночная с `<strong>Назначение бизнес-процесса</strong>` и значением из README.
- `<h3>Упрощенная BPMN схема бизнес-процесса</h3>` + `<img alt="BPMN схема {bpName}" src="" />` + `<p>Файл-исходник: <a href="">{bpName}.bpm</a></p>`.
- 1-колоночная таблица **Выходные данные бизнес-процесса** (письмо с результатами / иное из README).

### `id="Сценарий использования"` — Сценарий использования (перечень Steps)
`<table><tbody>` 2-колоночная (без thead): колонка 1 — `<a href="">{bpName}-Step-0N</a>`, колонка 2 — имя шага. По одной строке на каждый Step в порядке из шага 3.

### `id="Возможные исключения"` — Возможные исключения (Exceptions)
`<table>` с `<thead>` 4 колонки: `№`, `Описание`, `Тип исключения`, `Действие Bot при наступлении`. `<tbody>` — по строке на каждое `BusinessException` из Java. ID в первой колонке: `<a href="">{bpName}-EX-01</a>`. Тип: `Системное` / `Бизнес`. Действие Bot — нумерованный `<ol>` (отправить нотификацию, остановить процесс и т.п.).

### `id="Конфигурируемые параметры"` — Конфигурируемые параметры
Вводный `<p>` + `<p>` про группу ресурсов. `<table>` с `<thead>` 5 колонок: `№`, `Параметр`, `Ресурс`, `Описание`, `Текущее значение`.
- Использует `rowspan` для группировки параметров одного ресурса (см. шаблон: `emailRecipients:to/cc/bcc` в одном блоке `rowspan="3"`).
- Источник: все ключи верхнего уровня из init_params.json. Ресурс — имя init_params-ресурса процесса (например `<module>_initial_params`).

### `id="Нотификации"` — Нотификации
`<table>` с `<thead>` 6 колонок: `№`, `Наименование`, `Ресурс`, `Описание`, `Текущее значение`, `Тип`.
- По строке на каждый шаблон из email_templates.json. Наименование — ключ шаблона. Текущее значение — `subjectTemplate`/`bodyTemplate` (можно FreeMarker `${...}`). Тип — `Email` / `SMS`.

### `id="Конфиденциальные значения"` — Конфиденциальные значения
Вводный `<p>` + `<p>` со ссылкой на [Интеграции со сторонними системами](https://wiki.a1.by/pages/viewpage.action?pageId=407798383) (ссылка постоянная). `<table>` с `<thead>` 4 колонки: `№`, `Ресурс`, `Группа`, `Описание`. Источник: все `getCredentials(...)` вызовы из Java.

### `id="Прочие ресурсы"` — Прочие ресурсы
`<table>` с `<thead>` 5 колонок: `№`, `Ресурс`, `Группа`, `Описание`, `Текущее значение`. Источник: все `assets().get(...)` вызовы из Java (не-credential).

### `id="Хранилище"` — Хранилище
`<table>` с `<thead>` 3 колонки: `№ п/п`, `Наименование папки в Хранилище`, `Описание`. Папки из Orchestrator Storage (из README / Java, `UnifiedFoldersUtil`).

### `id="Папки доступа"` — Папки доступа
`<table>` с `<thead>` 4 колонки: `№ п/п`, `Наименование папки доступа`, `Описание`, `Перечень объектов, которым присвоена папка` (последнее — `<ul>` из Actions). Источник: README (раздел про папки доступа/Actions).

## Step-NN — описание шага

Шаблоны: `DemoBP-Step-01. Начало работы.html` … `DemoBP-Step-04. Завершение работы.html` → `{bpName}-Step-01.html` … `{bpName}-Step-{NN}.html`

Все Step-файлы имеют **идентичную 9-строчную таблицу** (`<table><tbody>`, без thead). Каждая строка: `<td><strong>Лейбл</strong></td><td>значение</td>`:

| # | Лейбл | Содержание |
|---|-------|------------|
| 1 | Идентификатор | `{bpName}-Step-{NN}` |
| 2 | Определение | Имя шага (bold) — из `@StepName`, camelCase → Title Case |
| 3 | Пользователь | `Bot` (для Java-шага) или `Исполнитель` (для самостоятельного MT/web-action — см. SKILL.md «Шаги сценария») |
| 4 | Входные данные | `<ul>` входов или `Не заданы` |
| 5 | Основной путь | `<ol>` действий Бота (из `execute()`) |
| 6 | Альтернативные пути | `—` или описание |
| 7 | Выходные данные | `<ul>` выходов (из `ProcessTransaction.set*()`) |
| 8 | Дополнительные требования | `—` |
| 9 | Возможные исключения | `<a href="">{bpName}-EX-NN</a>` |

Особый случай: Step-04 «Завершение работы» дополнительно содержит `<h2>Приложения</h2>` с 1-колоночной таблицей «Пример письма с результатом работы». Добавляй эту секцию только для финального шага, если он отправляет результирующее письмо.

## TD — Test Documentation

Шаблон: `DemoBP-TD - Test Documentation - Тестовая документация.html` → `{bpName}-TD - Test Documentation.html`

`<table>` с `<thead>` 6 колонок: `Проверяемая область`, `Описание тест-кейса`, `Условия выполнения`, `Ожидаемый результат`, `Критерий успешности`, `Полученный результат`. `<tbody>` с placeholder-строками (`Рабочая среда/проверяемый этап…`, `Условие 1_1_1` и т.д.) + финальная строка `...`.

Действие: это **чистый шаблон** — оставляй placeholder-структуру, не заполняй реальными тест-кейсами (тестовая документация ведётся отдельно). Только замени `DemoBP` → `{bpName}` если встречается.

## UG — User Guide

Шаблон: `DemoBP-UG - User Guide - Руководство пользователя.html` → `{bpName}-UG - User Guide.html`

Структура:
- `<h2>Общая информация</h2>` + `<table><tbody>` с 6 строками: Название бизнес-процесса, Управление, Владелец, Пользователи, Связанные документы (`<ul>` со ссылками на PDD и TD), Статус документа (равно статусу PDD).
- `<h2>Краткое описание процесса</h2>` + `<h3>Упрощенная BPMN схема…</h3>` + `<img alt="BPMN схема {bpName}" src="" />`.
- `<h2>Описание шагов процесса с точки зрения действий Исполнителя</h2>` + `<table>` с `<thead>` 4 колонки: `Шаг (со ссылкой на PDD)`, `Наименование`, `Действия Исполнителя`, `Действия Bot`. По строке на каждый Step (зеркалит PDD «Сценарий использования», но с разделением действий Исполнителя и Бота).
- `<h2>Работа Исполнителя с исключениями</h2>` + `<table>` с `<thead>` 4 колонки: `№`, `Описание`, `Тип исключения`, `Действие Исполнителя при наступлении`. По строке на каждое исключение (зеркалит PDD Exceptions, но действия — со стороны Исполнителя, а не Бота).

UG — это пользовательское зеркало PDD: те же шаги и исключения, но описанные с точки зрения Исполнителя.
