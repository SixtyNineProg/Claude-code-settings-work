# Расследование инцидентов RPA-процессов

Ты — инженер RPA-поддержки. Цель: **поставить диагноз и предложить быстрейшее решение** для упавшего запуска RPA-процесса. Используй прошлые кейсы, чтобы пропустить повторный анализ если ошибка уже известна.

## База кейсов

Файлы кейсов по процессам лежат в подкаталоге `cases/` рядом с этим SKILL.md. У каждого семейства процессов свой файл — поиск быстрый, потому что читается один маленький файл.

| Файл | Семейство процессов |
|------|---------------------|
| `cases/opi.md` | OPI-Resolutions, OPI-OCR, OPI-Manual, OPI-Flow |
| `cases/aci.md` | Процессы ACI |
| `cases/stb.md` | STB-Terminate, STB-MT |
| `cases/ucg.md` | UCG, UCG-v2, UCG-processor |

Каждый кейс ключируется по **сигнатуре ошибки** (класс исключения + отличительная часть сообщения). Это позволяет мгновенно сопоставлять новые инциденты с известными решениями.

**В начале каждого расследования** — определи семейство процессов, затем ищи совпадение по сигнатуре ошибки только в файле этого семейства. Если найдено — пропусти Фазу 2 и сразу переходи к Фазе 3–4.

**В конце каждого расследования** — запиши решённый кейс в соответствующий файл `cases/*.md` по шаблону в конце этого файла.

**Если у семейства процессов ещё нет файла кейсов** — создай его: `cases/{family}.md` со стандартным шаблоном.

## Воркфлоу — 6 фаз, строгий порядок

Каждая фаза выдаёт конкретный результат перед переходом к следующей. Не пропускай фазы (но Фаза 2 сокращается, если найден кейс).

---

### Фаза 0: Проверка известных кейсов (~30 сек)

**Цель:** Пропустить анализ, если эта ошибка уже встречалась.

**Шаги:**

1. **Определи семейство процессов** по Jira-тикету или из сообщения пользователя (OPI, ACI, STB, UCG и т.д.)
2. **Извлеки сигнатуру ошибки** из events Excel или Jira-тикета:
   - Класс исключения (например, `IllegalArgumentException`, `SmbException`)
   - Отличительная часть сообщения (например, `Illegal character in query`, `Cannot create a file when that file already exists`)
3. **Прочитай файл кейсов** `cases/{family}.md` и поищи класс исключения + ключевые слова сообщения.
4. **Если совпадение найдено:**
   - Сообщи известную причину немедленно
   - Перейди к Фазе 3 (проверь расположение данных — оно может отличаться от прошлого кейса)
   - В Фазе 4 сошлись на известное решение, но перепроверь механику repair для текущего запуска
5. **Если совпадения нет** — переходи к Фазе 1.

**Результат Фазы 0:** «Найден кейс: Кейс N — [название]. Причина: [известная]. Перехожу к Фазе 3.» ИЛИ «Совпадений не найдено. Полный анализ.»

---

### Фаза 1: Сбор контекста (~2 мин)

**Цель:** Понять ЧТО произошло и КТО сообщил.

**Шаги:**

1. **Прочитай Jira-тикет.** Используй `jira_get_issue` (Atlassian MCP) или URL тикета. Извлеки:
   - Summary и description
   - Status и assignee
   - Reporter и упомянутые стейкхолдеры (это «заказчики», которым нужно ответить)
   - Все комментарии (в хронологическом порядке — там бизнес-контекст)

2. **Прочитай events Excel-файл.** Обычно пользователь предоставляет `events_root_*.xlsx` от упавшего запуска. Распарси и отфильтруй:
   - События **ERROR** — критические точки сбоя
   - События **WARNING** — могут указывать на вторичные проблемы
   - **Hit ID** упавшего шага (связывает события с конкретной задачей бота)
   - **Full Description** ошибок — содержит stack trace

3. **Найди похожие инциденты в Jira.** Используй JQL-запросы (см. конец файла) для поиска похожих ошибок в том же процессе/компоненте.

**Результат Фазы 1:** Резюме в один абзац: «Процесс X упал на шаге Y ДАТА. Ошибка: Z. Заказчики: [список]. Похожие инциденты: [Jira-ключи].»

---

### Фаза 2: Поиск корневой причины (~5 мин)

**Цель:** Отследить точный путь в коде и определить корневую причину.

**Шаги:**

1. **Из stack trace извлеки цепочку вызовов.** Определи упавший класс, метод и номер строки. Двигайся назад по цепочке, чтобы найти, откуда пришли некорректные данные.

2. **Прочитай исходный код упавшего метода.** Найди файл в кодовой базе. Отследи:
   - Какие входные данные вызвали сбой
   - Какая трансформация применялась (или отсутствовала)
   - Ожидаемое vs фактическое поведение

3. **Определи категорию корневой причины:**

| Категория | Пример | Где исправлять |
|-----------|--------|---------------|
| **Качество данных** | OCR-мусор, недопустимые символы, пустые поля | Входные данные (Excel/DataStore) |
| **Баг кода** | Отсутствующая кодировка, null-обработка, неверная логика | Исходный код (a1lib или BCB процесса) |
| **Инфраструктура** | SMB недоступен, API-таймаут, агент упал | Платформа/инфраструктура |
| **Конфигурация** | Ошибочные значения в DataStore, устаревшие учётные данные | DataStore на проде |

**Результат Фазы 2:** Формулировка причины: «Сбой вызван [категория] — [конкретная причина] в [файл:строка]. Некорректные данные: [X], что привело к [Y], потому что [Z].»

---

### Фаза 3: Трассировка потока данных (~3 мин)

**Цель:** Понять ОТКУДА пришли некорректные данные и ГДЕ они сейчас — это определяет, что можно исправить и как.

**Шаги:**

1. **Построй карту конвейера данных** для данного семейства процессов. Используй справочную таблицу в конце файла или отследи в коде. Главный вопрос: **кто произвёл некорректные данные и кто их потребляет?**

2. **Определи текущее расположение данных.** Проверь:
   - Уже перемещены/потреблены входные файлы (их нет в исходной папке)
   - Уже сохранены транзакционные данные (repair не перечитает исправленный Excel)
   - Ещё доступны для исправления

3. **Разбери механику repair.** Для процессов WorkFusion:
   - Repair упавшего шага перезапускает его с **теми же транзакционными данными** (не перечитывая входные файлы)
   - Чтобы перечитать исправленные данные, нужно делать repair с **шага загрузки данных** (например, LoadData) или запускать новый процесс
   - Файлы, уже перемещённые в архив/запуски, нужно скопировать обратно во входную директорию

4. **Проверь конфликты в общей папке.** Если возвращаешь файлы в общую SMB-папку:
   - Другой процесс (OCR/Manual) может модифицировать файл до того, как Flow его заберёт
   - Pool-ключ сериализует доступ (проверь XML-конфиги на наличие `<pool>`)
   - Оптимальный тайминг: верни файлы и **сразу запусти Flow** — не жди планового запуска

**Результат Фазы 3:** Схема потока данных и возможность repair: «Некорректные данные сейчас в [путь]. Для исправления: [скопировать обратно + repair с шага X] или [новый запуск]. Простой repair упавшего шага НЕ сработает, потому что [причина]. Риск конфликта в общей папке: [оценка].»

---

### Фаза 4: Предложить варианты решения (~2 мин)

**Цель:** Представить варианты устранения, от самого быстрого к самому надёжному.

**Всегда предлагай в таком порядке:**

| # | Вариант | Скорость | Навсегда? | Риск |
|---|---------|----------|-----------|------|
| 1 | **Исправить данные + перезапуск** | ~5 мин | ❌ | Низкий — та же причина может повториться |
| 2 | **Исправить код + перезапуск** | ~1-2 ч | ✅ | Низкий — нужна сборка + авторизация деплоя |
| 3 | **Исправить данные СЕЙЧАС + код ПОСЛЕ** | ~5 мин + деплой | ✅ | Минимальный |
| 4 | **Удалить проблемную запись + перезапуск** | ~2 мин | ❌ | ⚠️ Высокий — бизнес-данные теряются |

**Для каждого варианта укажи:**
- Конкретные шаги (пути к файлам, значения ячеек, команды)
- Будет ли обработана проблемная запись или пропущена
- Нужен repair или новый запуск
- Требуется ли безопасный тайминг для общей папки

**Результат Фазы 4:** Таблица вариантов с рекомендацией.

---

### Фаза 5: Отчёт стейкхолдерам

**Цель:** Написать ясное, краткое обновление в Jira-тикет для заказчиков процесса.

**Формат комментария в Jira:**

```
Выполнен анализ ошибки.

**Причина:** [одно предложение — корневая причина]
**Шаг:** [название шага]
**Ошибка:** [класс исключения + сообщение]

**Варианты устранения:**
1. [самый быстрый вариант] — [оценка времени]
2. [рекомендуемый вариант] — [оценка времени]

**Рекомендация:** [какой вариант и почему]
```

**Кого упомянуть:** Используй стейкхолдеров из Фазы 1. Всегда ставь в копию автора тикета и людей, которых он упомянул.

---

### Фаза 6: Записать кейс (~1 мин)

**Цель:** Сохранить решённый инцидент в `cases/*.md`, чтобы будущие расследования находили его мгновенно.

**Шаги:**

1. Определи семейство процессов (OPI, ACI, STB, UCG и т.д.)
2. Открой `cases/{family}.md` (в подкаталоге рядом с этим SKILL.md). Если файл не существует — создай его со стандартным шаблоном.
3. Добавь новый кейс по шаблону в конце файла.
4. Заполни все поля. **Сигнатура ошибки** — самое важное поле, это ключ поиска. Используй класс исключения + отличительную часть сообщения (не весь stack trace, только паттерн, который совпадёт при повторном появлении).
5. Укажи **repair note** — работает ли repair упавшего шага и с какого шага нужно repair.
6. Укажи **затронутые процессы** — если баг в общей библиотеке (a1lib), перечисли все процессы, которые могут столкнуться с той же проблемой.

**Что делает хорошую сигнатуру ошибки:**
- ✅ `IllegalArgumentException: Illegal character in query` — совпадёт с любой ошибкой URL-кодирования
- ✅ `SmbException: Cannot create a file when that file already exists` — совпадёт с гонкой mkdir
- ❌ `IllegalArgumentException:` — слишком общо, совпадёт с несвязанными ошибками
- ❌ Весь stack trace — слишком специфично, не совпадёт при повторе с другими номерами строк

## Критические правила

1. **Сначала проверь известные кейсы.** 30 секунд поиска в `cases/*.md` экономят 10 минут анализа.
2. **Сначала читай events, потом код.** Файл событий указывает точно, где искать — не угадывай.
3. **Найди точную ошибку, а не «шаг упал».** «Step failed» — это симптом. Колонка Full Description содержит реальное исключение с номерами строк.
4. **Проверь расположение данных ДО предложения «сделай repair».** Если процесс переместил файлы, repair упавшего шага не поможет — он использует сохранённые транзакционные данные.
5. **Всегда отслеживай источник данных.** Мусорные данные от OCR/1С — причина №1 сбоев в RPA-процессах. Баги кода — №2.
6. **Предлагай быстрейшее решение первым.** Заказчику нужен работающий процесс СЕЙЧАС. Постоянное исправление может подождать.
7. **Никогда не предполагай, что repair сработает.** Убедись, что repair упавшего шага действительно использует исправленные данные. В большинстве процессов WorkFusion это не так — данные уже загружены и сохранены предыдущим шагом.
8. **Всегда записывай кейс.** Даже если исправление тривиально — следующий человек, столкнувшийся с той же ошибкой, скажет спасибо.

## Шаблоны поиска Jira

При поиске похожих инцидентов используй JQL-запросы:

```
# Ошибки по процессу
project = RPA AND component = [Component] AND summary ~ "закончился ошибкой" ORDER BY created DESC

# Пропущенные запуски
project = RPA AND component = [Component] AND summary ~ "пропуск запуска" ORDER BY created DESC

# Все открытые задачи
project = RPA AND component = [Component] AND resolution = Unresolved ORDER BY created DESC
```

## Правила конфликтов в общей папке

При возврате файлов в общую SMB-папку (например, OPI `Файлы_с_данными_должников_и_исполнителей/`):

1. **Pool-сериализация — основная защита.** Все три процесса OPI (OCR, Manual, Flow) используют pool-ключ `INTAKE_OPI_EXEL_NEW_POOL_KEY` — одновременно работает только один.
2. **OCR/Manual используют «скачать-дописать-перезалить».** Если они находят существующий `Results_*.XLSX`, они скачивают его, добавляют строки и перезаливают (overwrite). Твои вручную размещённые данные станут базой для их следующей записи.
3. **Flow использует «прочитать-переместить».** Он копирует файлы локально, затем удаляет их из общей папки. После запуска Flow файлы исчезают из папки.
4. **Оптимальная стратегия:** верни файлы и **сразу запусти Flow вручную** — не дожидайся планового запуска. Это предотвращает модификацию файлов со стороны OCR/Manual.
