## Кейс 1: Недопустимый символ в URI-запросе (OPI-Flow CheckSubscribers)

**Дата:** 2026-06-12
**Jira:** RPA-17822
**Процесс:** OPI-Flow
**Шаг:** CheckSubscribers
**Сигнатура ошибки:** `IllegalArgumentException: Illegal character in query`
**Категория причины:** Баг кода — неполная URL-кодировка
**Причина:** `UserUtils.openApiUrlEncode()` в `a1lib` (строка 186) кодирует только 4 символа (`%`, пробел, `&`, `?`). Символы `^`, `'`, `#`, `{`, `}` проходят без кодировки → `URI.create()` бросает исключение.
**Данные-триггер:** OCR-распознанное отчество `Владимировы^'` (мусорные символы из скана)
**Исправление (код):** Заменить тело `openApiUrlEncode` на `URLEncoder.encode(parameter, "UTF-8").replace("+", "%20")`. Добавить импорты `java.net.URLEncoder`, `java.io.UnsupportedEncodingException`.
**Исправление (данные):** Исправить значение ячейки в `Results_Svetlana_Poplavskaya.XLSX` (в `Запуски/2026/Июнь/12_184502/`), вернуть файлы в `Файлы_с_данными_должников_и_исполнителей/`, перезапустить с шага LoadData.
**Repair:** Repair шага CheckSubscribers НЕ работает — он перерабатывает те же сохранённые транзакционные данные с `Владимировы^'`. Необходимо repair с шага LoadData (перечитает Excel) или новый запуск.
**Общая папка:** Возврат файлов безопасен. Pool-ключ `INTAKE_OPI_EXEL_NEW_POOL_KEY` сериализует доступ OCR/Manual/Flow. Вернуть файлы + сразу запустить Flow вручную — чтобы OCR/Manual не успели модифицировать файлы раньше.
**Исторический прецедент:** RPA-15069 — тот же класс проблемы (мусор в DataStore `opi_autocomplete_patronymics`).
**Затронутые процессы:** Все процессы, использующие `UserUtils` из `a1lib` — OPI-Flow, ACI, UCG, UCG-v2, STB-Terminate, STB-MT.

## Кейс 4: HTTP 404 при проверке отсутствующего файла Orchestrator Storage

**Дата:** 2026-09-02
**Jira:** RPA-16084
**Процесс:** SOX_CI_LIST_ICS_60112 task creator
**Шаг:** MainJsdStep — сохранение отчёта в StorageService
**Сигнатура ошибки:** `NetworkException: Operation 'check file exists' failed: HTTP 404`
**Категория причины:** Баг кода — HTTP 404 отсутствующего файла ошибочно считался сетевой ошибкой
**Причина:** `rpa-core` `FileOperationsImpl.checkFileExists` передавал HTTP 404 от `GET api/files/read/{fileName}` в общий `ErrorHandler`, хотя для операции проверки существования 404 означает отсутствие файла. Ошибка возникала и во внешней проверке `StorageService`, и во внутренней проверке перед upload.
**Данные-триггер:** Новый отчёт отсутствовал в Orchestrator Storage; SharePoint upload при этом успешно завершался.
**Исправление (код):** В `FileOperationsImpl.checkFileExists` обрабатывать только HTTP 404 как `false`; остальные неуспешные статусы должны оставаться исключениями. Добавлен регрессионный тест для 404 и прохождения upload после отсутствующего файла.
**Исправление (данные):** Не требуется.
**Repair:** Простой repair шага до обновления `rpa-core` не сработает. После деплоя исправленной версии `rpa-core` повторить запуск/repair `MainJsdStep`; SharePoint-файл уже создан, а Storage-файл будет загружен.
**Общая папка:** Не относится к общей SMB-папке; данные отчёта уже сформированы и загружены в SharePoint.
**Исторический прецедент:** Регрессия после изменения `FileOperationsImpl` в коммите `b8d87d9`.
**Затронутые процессы:** Все процессы, использующие `rpa-core` Orchestrator `files().exists(...)`, `files().upload(...)` или другие операции с отсутствующими файлами.

## Кейс 5: UnknownHostException из-за передачи схемы в legacy SharePointClient

**Дата:** 2026-09-07
**Jira:** RPA-16084
**Процесс:** SOX_CI_LIST_ICS_60112 report creator
**Шаг:** JsdTaskHandlerStep
**Сигнатура ошибки:** `UnknownHostException: No such host is known (https://vactpro.main.velcom.by)`
**Категория причины:** Баг кода — legacy `SharePointClient` получил URL со схемой вместо bare hostname
**Причина:** `ProcessServiceFactory.buildUrl` добавлял `https://`, а legacy `SharePointClient.buildHttpHost` передаёт значение целиком в `new HttpHost(spBase, 443, "https")`; Apache пытался разрешить DNS-имя `https://vactpro.main.velcom.by`.
**Данные-триггер:** Конфигурация содержит корректный bare host `vactpro.main.velcom.by`; ошибка появилась после перехода с V2 SharePoint API на legacy API.
**Исправление (код):** Передавать в legacy client только hostname, удаляя `http://`, `https://` и завершающие `/`; HTTPS и порт 443 задаются самим legacy client.
**Исправление (данные):** Не требуется. DNS и TCP/443 на агенте проверены: имя разрешается в `10.254.5.97`, TCP-соединение успешно.
**Repair:** После сборки и деплоя исправленного JAR повторить `JsdTaskHandlerStep`; простой repair старого JAR не поможет.
**Общая папка:** Не относится к общей SMB-папке.
**Исторический прецедент:** Регрессия в рамках RPA-16084 при миграции SharePoint API.
**Затронутые процессы:** Текущий report creator; проверить другие процессы, мигрирующие на legacy `SharePointClient`.

**Исправление (данные):** Не требуется.
**Repair:** Не требуется; после деплоя исправленного JAR выполнить новый запуск или repair соответствующего шага.
**Общая папка:** Папка создаётся на SMB, но при `manual=0` после исправления не создаётся.
**Исторический прецедент:** Исходный процесс `wf_odf/ODF/opi/opi-ocr` создавал manual-каталог лениво в `filesMoveToManual()`.

## Кейс 7: Connection refused при подключении к OpenAPI production endpoint

**Дата:** 2026-09-18
**Jira:** Не указан
**Процесс:** OPI-Flow
**Шаг:** CheckSubscribers
**Сигнатура ошибки:** `OpenApiException` + `ConnectException: Connection refused` к `srv-lb-prod:8084`
**Категория причины:** Инфраструктура или конфигурация — TCP-соединение отвергнуто до получения HTTP-ответа; фактический runtime endpoint отличается от tracked-конфигурации
**Причина:** `OpiOpenApiClientFactory` берёт host и port из сохранённых runtime init-параметров. В stack trace использован `srv-lb-prod/10.254.13.100:8084`, хотя tracked `prod/opi_flow_init_params.json` содержит `http://srv-lb-qa:8084`; требуется проверить источник runtime override и listener/LB/backend на production endpoint.
**Данные-триггер:** Runtime-конфигурация с `openApiUrl=srv-lb-prod` либо недоступность `10.254.13.100:8084` с агента запуска.
**Исправление (код):** Не требуется для самой ошибки подключения. Если подтверждена нормативность `srv-lb-prod`, исправить инфраструктуру; если нормативен QA, исправить источник runtime-конфигурации. Не переключать production на QA без согласования.
**Исправление (данные):** Не требуется; проверить сохранённые init-параметры и состояние уже выполненных операций перед повтором.
**Repair:** Сначала восстановить endpoint или исправить deployment/runtime asset. Простой repair старого шага не меняет сохранённые init-параметры; после исправления выполнить один контролируемый repair/новый запуск с проверкой отсутствия дублей tickler/SMS.
**Общая папка:** Не относится непосредственно к общей SMB-папке; перед повтором проверить состояние входных файлов и ранее выполненных бизнес-операций.
**Исторический прецедент:** Новый кейс; ближайшие кейсы 1 и 4 имеют другую причину.
**Затронутые процессы:** OPI-Flow и другие процессы, использующие тот же OpenAPI endpoint или production LB.

## Кейс 8: Коллизия имён при переносе в месячный архив (OPI-OCR)

**Дата:** 2026-09-29
**Jira:** Не указан
**Процесс:** OPI-OCR
**Шаг:** ParseResolutionsAutomaticallyStep
**Сигнатура ошибки:** `BusinessException: Cannot archive recognized document` + `jcifs.smb.SmbException: Cannot create a file when that file already exists`
**Категория причины:** Баг кода — перенос в архив не идемпотентен, архив плоский по месяцу и ключуется именем файла
**Причина:** `SMBService.moveFile` → `SmbFile.renameTo` без обработки существующей цели. `DirectoryLayout.archive()` = `Архив_распознанного/<год>/<месяц>/` — один каталог на месяц, ключ — имя файла. Если файл с таким именем уже заархивирован в этом месяце (раньше в том же месяце или возвращён поддержкой на переобработку), перенос падает.
**Данные-триггер:** `постановление о принятии меры по обеспечению.rtf` — имя без должника/номера (generic-название документа), уже присутствовало в `Архив_распознанного/2026/сентябрь/`; источник `Work/OCR/2026_сентябрь_29_100128/постановление о принятии меры по обеспечению.rtf`.
**Диагностический признак (важно):** jcifs-ng 2.1.6 `SmbFile.java:1331` сначала проверяет существование источника (`NT_STATUS_OBJECT_NAME_NOT_FOUND` при его отсутствии). Ошибка коллизии означает, что **источник на месте**, т.е. это не повторная архивация своего же файла в том же запуске, а конфликт с архивной копией прошлого прогона.
**Исправление (код):** Не сделано. Требуется: идемпотентный перенос в архив (проверка цели / уникальное имя / подпапка `Оригиналы`) + защита от повторной дописи отчёта (повторный вызов `appendRecognized` дублирует строки).
**Исправление (данные):** Довести архивацию вручную: перенести оставшиеся `.rtf` из `Work/OCR/<run>/` в `Архив_распознанного/2026/сентябрь/`, предварительно переименовав уже лежащую одноимённую копию. Без repair и без перезапуска процесса.
**Repair:** Repair `ParseResolutionsAutomaticallyStep` НЕ работает и вреден: он заново прочитает `DocumentState`, снова вызовет `appendRecognized` (строка 93 идёт ДО архивации) → дубли строк в `Results_System.XLSX` → дубли SMS/тиклеров/обзвона в OPI-Flow, а затем упадёт на той же коллизии. Repair `PrepareFilesStep` бесполезен: входная папка уже пуста.
**Общая папка:** `Файлы_с_данными_должников_и_исполнителей/Results_System.XLSX` **уже дописан до сбоя архивации** — потери данных нет. Проверить, не забрал ли Excel OPI-Flow (папка `Запуски/`): если нет — дубли можно убрать до попадания в обзвон.
**Исторический прецедент:** Новый кейс. Ближайший по механике — Кейс 6 (жизненный цикл папок OCR), но причина другая.
**Затронутые процессы:** OPI-OCR (перенос в `Архив_распознанного`). Проверить все процессы, архивирующие по плоскому месячному пути с ключом-именем файла.
