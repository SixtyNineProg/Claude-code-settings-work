# Да, всё в порядке — противоречия здесь нет

`cron_tab = 0 9 * * *` и `last_run = 2026-10-01T06:00:00Z` **согласуются друг с другом**. Это не
ошибка в расписании и не сбой запуска, а ровно та ситуация, которая выглядит как расхождение,
пока не учтён часовой пояс.

## Почему числа выглядят разными

`cron_tab` считается в **местном времени Sherpa — Минск, UTC+3**, а API `/schedules` отдаёт
`last_run` (как и `created`, `enabled_at`) **в UTC**. Отсюда фиксированное расхождение в 3 часа:

| | Значение |
|---|---|
| По расписанию | 09:00 по Минску |
| `last_run` в UTC | `06:00:00Z` |
| `last_run` + 3 ч = Минск | **`09:00`** |

`06:00Z` + 3 часа = `09:00` по Минску — то есть ровно то время, которое задаёт выражение. Проверка
сходится точно, до минуты: запуск был сегодня, 1 октября 2026, в 09:00 по Минску.

## Расшифровка выражения

**`0 9 * * *`** — пять полей POSIX (`минута час день_месяца месяц день_недели`):

- `0` — минута: нулевая;
- `9` — час: 9 часов;
- `*` — день месяца: любой;
- `*` — месяц: любой;
- `*` — день недели: любой.

Человеческим языком: **каждый день в 09:00 по Минску (UTC+3)**.

## Ближайшие запуски (вывод скрипта)

```text
$ python scripts/cron_next.py "0 9 * * *" -n 5 --from 2026-10-01T00:00
cron_tab: 0 9 * * *
Поля:     мин=[0]  час=[9]  д.мес=*  мес=*  д.нед=*
Часовой пояс: Europe/Minsk (UTC+3, фиксированное смещение — базы tzdata нет) — cron считается
в локальном времени Sherpa
Следующие 5:
  2026-10-01 09:00 Чт
  2026-10-02 09:00 Пт
  2026-10-03 09:00 Сб
  2026-10-04 09:00 Вс
  2026-10-05 09:00 Пн
```

Выражение валидно (`valid: true`, код возврата 0, `warnings` пуст). Первый запуск в списке —
сегодняшний, `2026-10-01 09:00` по Минску, что в UTC ровно `2026-10-01T06:00:00Z`. Это и есть
зафиксированный `last_run`.

## Что стоит держать в голове

- Если смотреть на выгрузку `/schedules` «на глаз», без поправки на пояс, кажется, что задача
  стартует в 06:00 — но это не так: в UTC она стартует в 06:00, а фактически, по часам Минска,
  в 09:00. Согласовывать эти числа в голове не нужно — сдвиг всегда постоянный, +3 часа.
- Отдельно проверять нечего: расхождение объясняется полностью, «необъяснённого» остатка нет.

## Сделанные допущения

- Смещение `Europe/Minsk` принято фиксированным **UTC+3** — как это делает сам скрипт (базы
  tzdata в окружении нет). Для Минска это верно: переходов на летнее время с 2011 года нет.
- Предполагается, что `cron_tab` и `last_run` относятся к одной и той же записи расписания и что
  задача с прошлого запуска не меняла выражение. Если `0 9 * * *` было выставлено уже **после**
  последнего запуска, то `last_run` относится к прежнему расписанию — тогда его нужно сравнивать со
  старым выражением, а не с текущим.

Вывод: **всё в порядке, задача отработала по своему расписанию.**
