# Расписание `0 9 30 2 *` — следующего запуска не будет

**Короткий ответ: у этого расписания следующего запуска нет — и не будет никогда.** Выражение
синтаксически корректно, Sherpa его примет без ошибки, но процесс по нему не стартует ни разу.

## 1. Расшифровка выражения

Поля стандартные для `cron_tab` — `минута час день_месяца месяц день_недели`:

| Поле | Значение | Смысл |
|---|---|---|
| минута | `0` | 0-я минута |
| час | `9` | 9 часов |
| день месяца | `30` | 30-е число |
| месяц | `2` | **февраль** |
| день недели | `*` | любой |

Человеческим языком: **«каждый год 30 февраля в 09:00 по Минску»**.

## 2. Почему запуска не будет

В феврале не бывает 30-го числа — ни в обычный год, ни в високосный. Максимум 28 (29 в
високосный). Значит, условие «день месяца = 30 И месяц = февраль» не выполняется никогда, и
выражение не сработает ни разу за весь срок жизни процесса.

Это не ошибка синтаксиса, а ошибка смысла, и опасна она именно этим: Sherpa сохранит расписание
молча, задача будет выглядеть «настроенной», а запусков не будет ни одного. В логах при этом не
появится ни слова о проблеме.

## 3. Вывод скрипта `scripts/cron_next.py`

```bash
python scripts/cron_next.py "0 9 30 2 *"
```

```
ПРЕДУПРЕЖДЕНИЕ: выражение разобрано, но за 5 лет ни разу не срабатывает — проверьте день месяца
и месяц (например, 30 февраля не существует)
cron_tab: 0 9 30 2 *
Поля:     мин=[0]  час=[9]  д.мес=[30]  мес=[2]  д.нед=*
Часовой пояс: Europe/Minsk (UTC+3, фиксированное смещение — базы tzdata нет) — cron считается
в локальном времени Sherpa
Срабатываний нет.
```

В режиме `--json` то же самое: `"valid": true`, `"next": []` — разобрано, но ближайших запусков
список пуст. Проверка идёт по горизонту в 5 лет; для 30 февраля этого более чем достаточно, так
как такого дня не существует ни в одном году. (Для сравнения: 29 февраля существует, и скрипт
его находит — ближайшее `2028-02-29T09:00:00`.)

## 4. Что вы, скорее всего, имели в виду

Ниже — проверенные тем же скриптом варианты. Выберите подходящий по смыслу:

**а) Последние дни февраля** — если «30 февраля» было попыткой сказать «конец февраля»:

```
0 9 28,29 2 *
```

```
Следующие 4:
  2027-02-28 09:00 Вс
  2028-02-28 09:00 Пн
  2028-02-29 09:00 Вт
  2029-02-28 09:00 Ср
```

28 февраля — последний день февраля в обычном году, 29-е подхватывается только в високосный.
Именно «последний день февраля» cron не выражает: у него нет ни понятия `L`, ни номера вхождения
в месяце. Список `28,29` — ближайшее, что даёт cron без потери корректности.

**б) Раз в год, 29 февраля** — если нужен именно конец февраля в високосный год:

```
0 9 29 2 *
```

Срабатывает раз в 4 года: `2028-02-29 09:00`. Возможно, вы хотели «раз в год», а получили бы
«раз в четыре».

**в) 30-е число каждого месяца** — если месяц был указан по ошибке:

```
0 9 30 * *
```

```
Следующие 3:
  2026-10-30 09:00 Пт
  2026-11-30 09:00 Пн
  2026-12-30 09:00 Ср
```

Февраль из этого расписания всё равно выпадает — там нет 30-го числа.

**г) 30-е число каждого второго месяца** — если `2` означало «раз в два месяца»:

```
0 9 30 */2 *
```

```
Следующие 4:
  2026-11-30 09:00 Пн
  2027-01-30 09:00 Сб
  2027-03-30 09:00 Вт
  2027-05-30 09:00 Вс
```

Запуски идут по январю, марту, маю, июлю, сентябрю, ноябрю — февраль снова пропущен.

Если же вы имели в виду **30.02** в европейской записи «день.месяц» — это ровно тот же
несуществующий день, и ответ тот же.

А вот если поля перепутаны местами (`0 9 2 30 *`, то есть `30` попало в поле месяца), Sherpa
такую запись уже не примет:

```
ОШИБКА: месяц: значение вне диапазона 1–12 (в «30»)
```

## 5. Сделанные допущения

- Порядок полей — стандартный для `cron_tab` Sherpa: `минута час день_месяца месяц день_недели`.
  Именно поэтому `30` читается как день месяца, а `2` — как февраль.
- `2` — это номер месяца (февраль), а не день недели: в поле дня недели допустимы значения 0–7,
  где 2 — вторник, но здесь двойка стоит в поле месяца.
- Время трактуется в локальном времени Sherpa — Минск, UTC+3. То есть «09:00» — это 09:00 по
  Минску; в выгрузке `/schedules` тот же момент выглядел бы как `06:00:00Z`. В этом конкретном
  случае разница не важна: запусков нет вообще, поэтому `last_run` у задачи не появится.
- Горизонт проверки скрипта — 5 лет; для 30 февраля этого достаточно, день не существует ни в
  одном году.

## 6. Предупреждения

- Непроверенного синтаксиса в самом выражении нет: только цифры, `*` и стандартные поля — всё
  такое встречается в выгрузке прода. Ненумерованных ⚠-вариантов здесь не предлагаю.
- Предупреждение не про синтаксис, а про смысл: **`0 9 30 2 *` не сработает никогда**. Если
  расписание уже заведено в Sherpa с таким `cron_tab`, это надо считать дефектом настройки —
  процесс не запускается, и никакой ошибки при этом не возникает.
- `28 февраля` и `30-е число` — это «календарные правила»; если нужны конкретные числа отчётного
  периода, в проде принято перечислять их списком (`10 14 1,5,10,20,25,26,27,28,29,30,31 * *`).
