# Проектирование REST API

Этот скилл — не пересказ базовых принципов REST (ресурсы, методы, коды — это Claude уже знает). Здесь оставлены **только неоднозначные решения**, где разработчики регулярно ошибаются: выбор между похожими методами, граница между похожими статус-кодами и выбор стратегии версионирования. Используй это как набор критериев выбора, а не как учебник.

Когда применять: пользователь проектирует эндпоинт, выбирает метод/status-код для конкретной операции, решает, как версионировать, или просит ревью REST-контракта. Если задача — просто *вызвать* чужой готовый API (типично для RPA-интеграций), этот скилл скорее всего не нужен.

## Принцип, который объединяет все решения

Каждый выбор в REST-дизайне проверяй двумя вопросами:
1. **Идемпотентность** — приведёт ли повторный точно такой же запрос к тому же состоянию ресурса?
2. **Семантика конфликта** — это ошибка *входных данных* или ошибка *бизнес-правила*?

От ответов на эти два вопроса зависит метод и статус-код. Большинство ошибок проектирования — это путаница именно в них, а не незнание синтаксиса.

## Выбор HTTP-метода

Базовая семантика очевидна (GET — чтение, POST — создание, DELETE — удаление). Неочевидное — два места:

### PUT vs PATCH
- **PUT** — полная замена ресурса. Клиент отправляет *целое* представление; то, чего нет в теле, удаляется. Идемпотентен: повторный PUT с тем же телом даёт то же состояние.
- **PATCH** — частичное изменение. Клиент отправляет только изменяемые поля; остальное не трогается. Идемпотентен *только если операция детерминирована* (`{"autoRenew": false}` — идемпотентна; `{"balance": "+100"}` — нет, повторный запрос добавит ещё 100).

Решающее правило: если операция описывается как «изменить конкретное поле на конкретное значение» — это PATCH. Если «перезаписать ресурс целиком» — PUT. Когда сомневаешься — выбирай PATCH: он точнее выражает намерение и не заставляет клиента отправлять поля, которые он не знает.

### Идемпотентность как инструмент, а не свойство
Идемпотентность — не inherent-свойство метода, а свойство *конкретной операции*. `DELETE /item/{id}` идемпотентен (второй раз удалять нечего — состояние то же). `POST /transfer` с телом суммы — нет. Если операция должна быть безопасна к повторам (например, вебхук может прийти дважды) — проектируй её идемпотентной на уровне семантики, а не надейся на метод.

## Выбор статус-кода — граница 400 vs 409

Самая частая ошибка — вернуть `400 Bad Request` там, где нужен `409 Conflict`. Различие принципиальное:

- **400 Bad Request** — ошибка *валидации полей*: malformed-тело, отсутствие обязательного поля, неверный тип, нарушение формат-ограничения. Запрос синтаксически/схематически неверен, сервер даже не дошёл до бизнес-логики.
- **409 Conflict** — запрос корректен по форме, но *противоречит бизнес-правилу или текущему состоянию*: email уже зарегистрирован, пытаемся удалить то, что связано с другим ресурсом, нарушаем уникальность. RFC 7231 прямо рекомендует 409 для конфликтов с текущим состоянием ресурса.

Решающее правило: «запрос плохо сформирован или поле неверно?» → 400. «запрос корректен, но бизнес-правило запрещает?» → 409. RFC 9110 описывает 409 как «конфликт с текущим состоянием целевого ресурса».

Другие часто путаемые пары:
- **201 vs 200** при создании: 201 Created + Location-заголовок на новый ресурс; 200 — если создаёшь как побочный эффект и не хочешь подчёркивать.
- **204 vs 200** при отсутствии тела: 204 No Content когда ответ пустой по дизайну (особенно после DELETE/PUT), 200 — когда есть тело.
- **404 vs 410**: 404 — «не знаю о ресурсе», 410 Gone — «знаю, что был и намеренно удалён» (используй редко, когда важно отличить).

## Версионирование — выбор стратегии

Версионирование закладывают с первого дня, а не добавляют потом. Три варианта, один запрещён:

| Стратегия | Когда применять | Плюсы / минусы |
|-----------|-----------------|----------------|
| **URL**: `/v1/...`, `/v2/...` | Внутренние и B2B-API | Явно, видно в логах/кэше, тривиально маршрутизируется. Минус: «версия» — не часть ресурса, формально загрязняет URL. |
| **Accept-заголовок + media type**: `Accept: application/vnd.x.v2+json` | Публичные API с долгосрочной поддержкой и множеством версий | URL остаётся чистым, можно версионировать отдельные представления. Минус: незаметно в логах, сложнее тестировать руками. |
| **Query-параметр**: `?version=2` | **Не использовать** | Кэшируется некорректно, неоднозначно с другими query, ломает промежуточные прокси. |

Решающее правило: для внутренних сервисов и B2B-интеграций (включая RPA-связки) — URL-версионирование `/v1/`. Это явнее всего, проще отлаживать, и именно его ожидает большинство клиентов. Accept-заголовок оправдан только для публичного API с долгим жизненным циклом и несколькими поддерживаемыми версиями. Никогда — `?version=`.

## Тело ошибки

Ошибка без тела — потерянный контекст для клиента. Минимальный контракт:

```json
{
  "code": "EMAIL_ALREADY_REGISTERED",
  "message": "Пользователь с таким email уже существует",
  "details": { "field": "email", "value": "user@example.com" }
}
```

`code` — машиночитаемый стабильный идентификатор (на нём строит логику клиент, поэтому не меняй его между версиями). `message` — человекочитаемый текст. `details` — опциональный контекст (имя поля, конфликтующее значение). Не возвращай стек-трейс и внутренние детали во внешние API.

## Финальный чек-лист (прогон перед сдачей контракта)

Пройдись по эндпоинту и проверь, что каждый пункт осознанно решён, а не остался «по умолчанию»:

1. URL идентифицирует **ресурс**, а не действие (`/subscriptions/{id}` ✓, `/disableAutorenew/{id}` ✗).
2. HTTP-метод соответствует операции, а не вставлен от балды.
3. Идемпотентность операции продумана — что будет при повторном запросе?
4. Статус-код выбран по семантике, не «верну 200 везде».
5. Ошибки имеют тело со стабильным `code` и человекочитаемым `message`.
6. Версионирование заложено с первого дня (для внутренних — `/v1/`).
7. Есть спецификация OpenAPI — контракт описан, а не только реализован.

Если по какому-то пункту ответ «не думал об этом» — это сигнал остановиться и додумать, прежде чем отдавать эндпоинт.
